# Flathub submission for org.echowire.app

**echowire is not on Flathub.** Nothing in this directory publishes anything. It
assembles the files a submission needs so the pull request is a review
conversation rather than a research project. Until that pull request is accepted,
do not advertise a Flathub listing anywhere, including the download page.

## Staging the files

```bash
fluxer_desktop/packaging/flathub/build-flathub-submission.sh out
```

That reads the live stable release descriptor, writes
`org.echowire.app.yml` with the matching archive url and sha256, and copies the
launcher, desktop entry, metainfo, scalable icon, the eight raster icons and
`flathub.json` beside it. The result is the complete content of the
`flathub/org.echowire.app` repository.

## Why this manifest installs a tarball instead of compiling

Flathub prefers a source build, and this manifest does not do one. The reason is
concrete rather than a preference:

- The desktop app is an Electron app inside a pnpm workspace that also builds a
  Rust native addon (`fluxer_desktop/native`). A Flathub build runs with **no
  network access**, so every npm and cargo dependency would have to be vendored
  into the manifest, generated by `flatpak-node-generator` and
  `flatpak-cargo-generator`. Against a pnpm monorepo with a native addon that is
  a large, separate piece of work, and the generated source list has to be
  regenerated on every dependency change or the build breaks.
- Electron itself would also need vendoring, because electron-builder downloads a
  prebuilt Electron during the build.

Installing our own published tarball, pinned by sha256 and auto-updated by
`flatpak-external-data-checker`, is the pattern several Electron apps on Flathub
already use. **A reviewer may still push back on it.** If they do, the options in
order of cost are: vendor the dependencies as above; or switch the manifest to
`extra-data`, which downloads the tarball on the user's machine at install time
instead of shipping it in the Flathub repository.

## What only you can do

1. **Make `cproudlock/echowire` public, or point the metainfo at a public
   mirror.** The repository is private today, so
   `https://github.com/cproudlock/echowire/issues` and the `vcs-browser` url in
   the metainfo both return 404 to everyone. Flathub expects an AGPL app's source
   to be reachable, and a reviewer will click those links.
2. **Own the domain in the app id.** `org.echowire.app` requires control of
   `echowire.org`, which is satisfied, and Flathub verifies it. Nothing to do
   beyond being the one who opens the pull request.
3. **Open the pull request.** Fork `flathub/flathub`, create a branch named
   `org.echowire.app`, commit the staged files at the repository root, and open a
   pull request against the `new-pr` branch. The submission has to come from the
   account that will maintain the listing.
4. **Answer the review.** Expect questions about `--device=all` (it is there for
   camera access in video calls; screen sharing already goes through the pipewire
   portal) and about the prebuilt tarball above.
5. **Keep the metainfo release entry current.** It is the one thing the checker
   does not update. A bump that leaves it stale publishes a version the app's own
   metadata does not mention.

## Local validation

Two of the checks Flathub runs need tools that are not installed in this
development container, so they have not been run here:

```bash
# validates the metainfo, including the releases entry and the screenshot
appstreamcli validate --explain org.echowire.app.metainfo.xml

# validates the manifest and the finish-args
flatpak run --command=flatpak-builder-lint org.flatpak.Builder manifest org.echowire.app.yml

# a real build, which also proves the tarball layout and the launcher path
flatpak run org.flatpak.Builder --force-clean --install --user builddir org.echowire.app.yml
```

`build-flathub-submission.sh` runs `appstreamcli validate` automatically when it
is present and says so plainly when it is not.
